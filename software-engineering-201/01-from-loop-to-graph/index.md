## The lesson

A loop makes one piece of work correct. A graph decides which pieces exist and which can run at the same time. Built around how three Software Engineering 101 lessons were made side by side, each with its own review.

## The rule

Before any job with more than one part, write down the pieces, and which can run at the same time. Then run each piece as its own loop, checked on its own.

This rule is written so an AI agent can follow it as a standing instruction.

## Transcript

Software engineering two oh one. Lesson one. From loop, to graph.

### Three pieces

Quick question to start. You've got three pieces of work. None of them needs anything from the others, and each one needs its own review. What's the fastest way through? One at a time, start to finish? All three, then one big review? Or three loops, side by side? Three loops. One at a time, every piece waits for the one before it. One big review, and the finished pieces wait for the slowest. Side by side, nothing waits for anything it doesn't need.

And that isn't a made-up example. It's how lessons three, four and five of Software Engineering one oh one were built. At the same time. Three scripts. Three independent reviews, running in parallel.

Follow lesson four. Its review, round one. Not yet.

Round two. Passed. And lessons three and five? Still going.

### Loop and graph

So what's underneath? In one oh one, each lesson was a loop. Plan, build, verify, repeat. A loop makes one piece of work correct. But somebody had to decide there would be three pieces. And that all three could run at the same time. That decision? That's the graph.

And that's the line between the two series. One oh one was the loop: getting one piece of work right. Two oh one is the layer above. How you split the work. What runs side by side. And how each run makes the next one better.

### An everyday graph

You already know this from cooking dinner. Each dish has a recipe. You taste. You adjust. You taste again. That's a loop.

But the evening is a graph. The rice simmers while you chop. The sauce waits for the onions. And everything has to land on the table together.

### In practice

Now picture the same three pieces, two ways. Handed to an agent as one long job, they run in a row, each one waiting for the last. Drawn as a graph, they run side by side. Same work. Far less waiting.

One thing doesn't change. The graph doesn't replace the loop. Every piece still gets planned, built and checked. The graph decides where the loops go.

So before any job with more than one part, ask three questions. What are the pieces? Does any piece need something from another? And which ones can start right now?

### The rule

Which gives us rule one, for your agents. Before any job with more than one part, write down the pieces, and which ones can run at the same time. Then run each piece as its own loop, checked on its own.

### Your turn

Now, your turn. Think of the last job you gave an agent that had more than one part. Write down the pieces. How many of them could have run at once?
